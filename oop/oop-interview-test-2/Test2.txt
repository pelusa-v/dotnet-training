- Polymorphism: The abilty of an object to execute a different behavior calling a method with the same name and giving part of the same parent class, using method overriding or method overloading. (example: The class Beast has a method Attack, that is a common attack, and the class GhostFeline that inherit from Beast has the method attack overriding the initial behavior, so, when you create an instance of a Beast and GhostFeline, you have two ojbjects of Beast class, but they both show different behavior when you call the method attack)

So now, the team 1 is working independently from the team 2, they just need the interface to go on work. When the team 2 built the SMSManager class implementing the ISMSSender interface with the SendMessage method, all will works good. This is a good approach because if we need to change the channel of communication of SMS or other sms logic, we only need to change the SMSManager class, giving the NetworkIssueNotificator class independent from this change. This is why our code is decoupled, making it more testable and easy to scale or change.

A- Yes, this pattern says ""open for extensions, closed for modifications", meaning that, while you're designing a class, you have to ensure the class can growth in methods, method overloading or properties, but won't require to refactor the current logic of methods for changes (reducing introducing bugs changing core methods, this is for making the class more scalable and easy to adapt). If we need to receive Juice tomorrow, we need to add another condition to the fill method with the Juice sound, so this class is not closed for modifications, making the code sensible to changes and easy to introduce bugs. This is how I would do it applying SOLID:

public class Bottle
{
    public ILiquid Content { get; private set; }

    public void Fill(ILiquid content)
    {
        Content = content;
        content.Sound();
    }
}

public interface ILiquid
{
    void Sound();
}

public class Soda : ILiquid
{
    public void Sound()
    {
        Console.WriteLine("Fizz");
    }
}

public class Water : ILiquid
{
    public void Sound()
    {
        Console.WriteLine("Splash");
    }
}

If we need to add juice, or other liquid, just need to receive other object implementing the ILiquid, so this class now is closed for modifications and open for extensions.

A- The repository pattern: You can add an abstraction layer to represent the persistence database, so we don't depend on the infrastructure database details, we just depend on the abstraction, methods that we're interested to apply over the db (CRUD for example). I use this pattern because allow me the ability to change the database engine or infrastructure specification without changing my business code, business code only depends on repository interfaces, not on db directly.
Example: 
case 1 (with repository pattern): serviceABC --> IRepositoryA <-- RepositoryA --> db (if change my db, this doesn't affect my services, and it's easy to test because I can replace the repository by an in memory repository implementing the interface for tests porpuses)
case 1 (without repository pattern): serviceABC --> db (if change my db, we also need to change my serviceABC)

Here is my structure and this is how I manage extensibility for new payment methods, the PaymentProcessor is the main class:

public class PaymentProcessor
{
    private INotificator _notificator;

    public PaymentProcessor(INotificator notificator)
    {
        _notificator = notificator;    
    }

    public void UserProcessPayment(User user, Order order)
    {
        try
        {
            ProcessPayment(user.PaymentMethod, order);
        }
        catch (Exception e)
        {
            Console.WriteLine(e.Message);
            _notificator.Notify("Payment failed", user);
            // Log the exception and notify the user
        }

        _notificator.Notify("Payment successful", user);
    }

    private void ProcessPayment(IPayable paymentMethod, Order order)
    {
        var result = paymentMethod.Pay(order.PaymentData);
        if (!result)
            throw new Exception("Payment failed");
        
        order.MarkAsPaid();
    }
}

public class User
{
    public PaymentMethodResource PaymentMethod { get; set; }
    // Some user data
    public User(PaymentMethodResource paymentMethod)
    {
        PaymentMethod = paymentMethod;
    }
}

public interface INotificator
{
    void Notify(string message, User user);
}

public class Order
{
    public PaymentDetails PaymentData { get; set; }
    // Some order data
    public Order(PaymentDetails paymentData)
    {
        PaymentData = paymentData;
    }

    public void MarkAsPaid()

        // Mark order as paid
    }
}
